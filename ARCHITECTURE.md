# Architecture

`schedule-my-agents` is a single-user, self-hosted calendar bridge that turns calendar events into verified, webhook-driven MCP Events deliveries for any MCP Events-compatible agent host. The primary Worker owns calendar authorization, provider sync, D1 persistence, setup UI, and `POST /mcp`. A separately deployed Cloudflare Worker (`dispatcher/`) stores opaque immutable alarms. Both deployments share this repository.

## Authority and scheduling

Provider registration (`lib/calendar/providers.ts`) owns credential refresh, authorization routes, change decoding, and cursor ordering. Notification ordering is rechecked under the sync lock; cursor commits happen before releasing the lock, after snapshot and alarm registration succeed. Snapshot/cursor writes and lock cleanup are fenced to the acquired lease so an expired sync cannot overwrite or unlock its successor. Shared occurrences use provider-neutral series and recurrence IDs, and persistence binds watches, snapshots, alarms, and receipts to a saved provider and connection identity. One active connection per owner is retained; replacing a connection requires disconnect and fresh consent. See [docs/calendar-provider-contract.md](docs/calendar-provider-contract.md).

`CalendarService` orchestrates consent, sync, invitations, write-back, maintenance, and MCP requests; `GoogleCalendar` (`lib/calendar/google.ts`) owns Google HTTP, recurrence expansion, and scoped write-back; `Store` (`lib/calendar/store.ts`) guards D1 commits. Provider push is authenticated using the persisted watch channel and current consent generation, independently of caller identity headers. Both the Worker entry point (`build/worker.ts`) and `CalendarService.handle` enforce `lib/calendar/auth.ts`: caller-supplied `x-authenticated-owner` is stripped and ignored unless `TRUST_PROXY_AUTH_HEADER=true` explicitly opts into a stripping reverse proxy. Setup routes (`/api/*`) accept a signed `sma_session` cookie or `ADMIN_SECRET` bearer; `POST /mcp` accepts only a separate `MCP_AUTH_TOKEN` bearer, so an MCP host can never change calendar grants, agent aliases, or allowlists. With neither configured, both fail closed with 401. Provider webhooks and alarm wakes carry their own channel or HMAC authority and receive no owner identity.

`CalendarMaintenance` (`lib/calendar/maintenance.ts`) runs from the Worker's `*/15 * * * *` `scheduled` cron trigger (and owner-scoped `POST /api/maintenance/run`). It cleans expired authorization state, renews owner-started watches within 24 hours of expiry, and resyncs watches with failed, missing, or 15-minute-stale syncs. Each calendar is isolated, and authority is rechecked before every renewal or sync.

After a successful sync, the bridge classifies event organizers (`lib/calendar/provenance.ts`) against the owner and the explicit `invite_allowlist`, blocking unallowlisted external invites at the integration layer. For allowed events that include registered `agent_aliases` as calendar guests (across both the 7-day snapshot and 366-day alarm candidates), it persists `agent_invitations` and dispatches `calendar.event.invited` onboarding webhooks independently per agent (with durable alarm retry on transient failure). It also registers opaque alarms for future standalone events and the next instance of each recurring series at start time (`leadTimeMinutes=0`) and at each active subscription's declared `leadTimeMinutes` (1–1440). Each alarm carries a random-IV AES-GCM envelope, opaque HMAC identity, UTC due time, and five-minute expiry. Only the bridge holds `ALARM_ENCRYPTION_KEY`. Owner, calendar, grant generation, and occurrence identifiers stay encrypted; event text never enters the envelope. Registration and wake callbacks use separate timestamped HMAC keys.

At wake time, the bridge decrypts the envelope, rechecks current connection and consent, and fetches the live occurrence from the provider. Cancelled, moved, revoked, or overdue occurrences are acknowledged without creating due work. A valid recurring occurrence registers only its next provider-expanded instance at the same lead time, then atomically claims per-agent due-work rows in `occurrence_outbox` after verifying alias registration, live guest membership, organizer allowlist status, and (for allowlisted external invites) explicit owner approval. A stale alarm never advances a series.

Owner-authorized calendar write-back is disabled by default per calendar (`write_back_enabled = 0`). When explicitly enabled, `calendar_rsvp` and `calendar_run_note` MCP tools validate owner consent, alias registration, live attendee membership, organizer allowlist/approval, and optimistic ETag matching before applying narrow RSVP or bounded run-status patches through `CalendarProvider.applyWriteBack`.

## Bounds and recovery

Discovery is bounded to 366 days, ten pages, and 500 candidate events or series; overflow fails explicitly. Callbacks within five minutes of start are accepted; the durable dispatcher persists retries with exponential delay up to 60 seconds and discards expired work after retaining a one-day tombstone and attempting cleanup. Logs contain opaque tags, outcomes, and timing, never event content, secrets, or envelopes.

## Subscriber delivery

Owner-scoped MCP subscriptions (`lib/calendar/subscriptions.ts`) persist encrypted signing secrets, finite expiry, key rotation, and idempotent unsubscribe in D1. Subscription verification and signed delivery share a validated-IP callback transport (`lib/calendar/callback-transport.ts`) backed by Go standard TLS/X.509 compiled to WASM (`tls-client/`) over raw TCP sockets to validated public IP addresses with original-hostname TLS verification.

Signed delivery (`lib/calendar/delivery.ts`) consumes due work through a persisted per-subscription ledger (`deliveries`) driven by the opaque alarm retries. Immutable serialized payloads and logical `evt_` IDs survive restarts; bounded leases, exponential backoff with injectable equal jitter, supported `Retry-After` hints, and a six-attempt limit bound retries within the five-minute lifetime. Every wake revalidates the provider occurrence, and each attempt rechecks current connection, calendar grant, and subscription authority before sending. Accepted HTTP 2xx receipts prove webhook delivery only, not agent execution. Event discovery (`events/list`) stays closed unless `MCP_EVENTS_READY=true`, alarms are configured, provider ingress is verified, and an enabled calendar grant exists.
