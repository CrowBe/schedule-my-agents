# Callback transport controls in the existing runtime

Research checked 8 October 2026. This supplements [the earlier security alternatives note](callback-security-alternatives-research.md), concentrating on implementable dial controls. It does not report new hosted test results or establish which upstream configuration Sites deploys. The existing exact OpenAI callback hostname, consent boundary, native delivery, and opaque timer are the scope; no service, credential, audience, or network-policy change was made.

## Usable candidates and elimination results

| Candidate | What it could establish | Evidence and current limitation |
| --- | --- | --- |
| Sites native fetch with runtime public-address filtering | Equivalent public-destination/DNS-rebinding protection if every actual dial and retry is filtered under the required range policy | Upstream enforcement exists, and Cloudflare describes global fetch as SSRF-safe. Sites wiring and range coverage remain to be established. This is the leading existing-infrastructure candidate. |
| Native HTTPS literal IP plus original `Host` | Application-selected address with original hostname identity, **only if** routing and TLS are independently controlled | No documented Workers fetch option supplies a separate TLS hostname. Standalone workerd follows the URL authority for address and TLS, and overwrites Host. Managed Cloudflare routing may differ; paired hosted probes can falsify the proposed mechanism. |
| `cf.resolveOverride` | Separate DNS destination for an eligible same-zone origin | Alternate hostname, restricted to the Worker's zone; external OpenAI callback is outside that supported use. |
| `node:https` custom Agent, lookup, or connector | Node's conventional validated-address HTTPS transport | Workers HTTPS wraps global fetch; Agent is a stub and socket/TLS dial controls are unavailable. |
| `node:net` lookup plus `node:tls` servername; a full Undici custom connector | A literal raw-socket dial with separate hostname TLS, if the managed socket backend supports both | **Lookup is implemented in upstream node:net.** It ultimately calls cloudflare:sockets; raw Cloudflare-IP restrictions remain. Expected TLS hostname override is marked unsupported in current socket source. Sites also documents raw sockets as unavailable. |
| Existing timer Worker as an opaque WebSocket-to-TCP bridge | Ciphertext relay without receiving event plaintext, with Site-side TLS identity | Mechanically possible as a protocol adapter, but its outbound TCP is the same restricted API. It cannot bypass blocked callback addresses, and adds no independently attested public-address guarantee. |
| Runtime fixed external-server binding | Fixed IP/port plus original certificate-host verification | Upstream workerd has precisely this operator capability. No corresponding supported Sites publishing capability was found. |
| Workers VPC Service / Network binding | Service configuration can separate connection target from URL Host/SNI | Requires pre-registered target and Tunnel/Mesh/network binding. None is established in the current infrastructure; adding it is outside this existing-infrastructure scope. |

The table's native-fetch candidate requires a destination policy, not necessarily selection of the earlier preflight IP. A runtime that validates each address immediately before dialing can remove the DNS time-of-check/time-of-use gap without exposing a caller-controlled resolver.

## Literal IP plus Host is not a documented pinning API

The [Workers Request contract](https://developers.cloudflare.com/workers/runtime-apis/request/#requestinitcfproperties) says `resolveOverride` changes the hostname used to determine the origin address while preserving URL Host, but is ignored unless both hosts are in the Worker's zone. It also restricts outside-zone Host overrides. Neither that contract nor the inspected RequestInit types documents `tlsServerName`, `authorityHost`, or another application option that independently selects the TLS reference identity.

Standalone workerd's underlying [KJ NetworkHttpClient](https://github.com/capnproto/capnproto/blob/3a82de9b39736a2625f03c93b2b7c50642dd5b25/c%2B%2B/src/kj/compat/http.c%2B%2B#L6019-L6151) overwrites the outgoing Host header with the parsed URL host, then resolves that same host using the TLS network for HTTPS. The [TLS network implementation](https://github.com/capnproto/capnproto/blob/3a82de9b39736a2625f03c93b2b7c50642dd5b25/c%2B%2B/src/kj/compat/tls.c%2B%2B#L579-L684) extracts the expected hostname from the address string; its [certificate check](https://github.com/capnproto/capnproto/blob/3a82de9b39736a2625f03c93b2b7c50642dd5b25/c%2B%2B/src/kj/compat/tls.c%2B%2B#L184-L218) verifies an IP literal against IP certificate identity and a hostname against hostname identity. Inference for this backend: an IP URL plus a manually supplied Host cannot preserve original-hostname TLS identity.

Cloudflare's managed proxy is not proven to be that standalone backend. Its [Origin Rules](https://developers.cloudflare.com/rules/origin-rules/features/) separately support Host, DNS and SNI overrides, and a Host rule updates SNI. Those are zone rules, not `fetch()` options; they cannot be imported into the Sites application contract. Likewise, the [VPC binding contract](https://developers.cloudflare.com/workers-vpc/api/#vpc-service) explicitly separates the configured target from URL Host/SNI, but only for that binding.

Therefore a successful HTTP response from `fetch("https://<IP>/", {headers:{Host: originalHost}})` is ambiguous: the proxy might route from the Host, use URL IP, reject a mismatch, or apply another managed rule. A target response, `cf-ray`, or requested-address string alone does not establish which address was dialed.

## The overlooked Node lookup path has real constraints

[Workers HTTP](https://developers.cloudflare.com/workers/runtime-apis/nodejs/http/#request) does not support `lookup` or `createConnection`. [Workers HTTPS](https://developers.cloudflare.com/workers/runtime-apis/nodejs/https/#other-differences-between-nodejs-and-workers-implementation-of-nodehttps) cannot expose its underlying socket or configure `servername`; its Agent is a stub. Swapping the high-level HTTP library does not add dial control.

However, upstream [node:net implementation](https://github.com/cloudflare/workerd/blob/cb61e82b35bf4cac7fc69821743337b8ca498bd5/src/node/internal/internal_net.ts#L1769-L1915) **does** invoke a custom lookup for a non-IP host, validate the returned IP/family, and pass that literal to internal `connect()`. Its `remoteAddress` is populated from this input and `autoSelectFamilyAttemptedAddresses` is constructed locally. These report the selected argument rather than an independently measured remote endpoint.

Upstream [node:tls](https://github.com/cloudflare/workerd/blob/cb61e82b35bf4cac7fc69821743337b8ca498bd5/src/node/internal/internal_tls_wrap.ts#L684-L742) forwards lookup and accepts explicit `servername`. The [TLS upgrade path](https://github.com/cloudflare/workerd/blob/cb61e82b35bf4cac7fc69821743337b8ca498bd5/src/node/internal/internal_tls_wrap.ts#L497-L526) passes it as `expectedServerHostname` to `startTls()`. But current [socket source](https://github.com/cloudflare/workerd/blob/cb61e82b35bf4cac7fc69821743337b8ca498bd5/src/workerd/api/sockets.c%2B%2B#L861-L943) labels that option unsupported, can reject it through an autogate, and otherwise delegates the TLS operation to the backend. Source availability therefore does not establish supported managed hostname verification.

The same [socket implementation](https://github.com/cloudflare/workerd/blob/cb61e82b35bf4cac7fc69821743337b8ca498bd5/src/workerd/api/sockets.c%2B%2B#L781-L797) supplies its requested `addressStr` as `remoteAddress`; the [opened result](https://github.com/cloudflare/workerd/blob/cb61e82b35bf4cac7fc69821743337b8ca498bd5/src/workerd/api/sockets.c%2B%2B#L1020-L1058) copies that string. `SocketInfo.remoteAddress` cannot be used as OS-peer attestation for this outbound path.

[Node net documentation](https://developers.cloudflare.com/workers/runtime-apis/nodejs/net/) confirms it is backed by cloudflare:sockets. [TCP socket policy](https://developers.cloudflare.com/workers/runtime-apis/tcp-sockets/#considerations) blocks Cloudflare IPs; its troubleshooting also identifies local/private addresses as disallowed. This applies equally to a custom Undici connector or the existing Worker TCP relay. [Undici Client](https://github.com/nodejs/undici/blob/main/docs/docs/api/Client.md#parameter-clientoptions) does offer a custom connector in Node, but that option is not evidence of a different Workers network primitive. The current installed Sites building contract (`sites/0.1.75/skills/sites-building/SKILL.md`) explicitly identifies raw TCP as unsupported in hosted Sites. Prior [hosted raw-socket evidence](sites-callback-support-repro.md) remains a separate observed failure.

## Platform controls and proof limits

The [workerd server schema](https://github.com/cloudflare/workerd/blob/cb61e82b35bf4cac7fc69821743337b8ca498bd5/src/workerd/server/workerd.capnp#L881-L981) has two relevant operator primitives: Network allow/deny CIDRs, including filtering resolved DNS addresses; and ExternalServer with fixed `address` plus HTTPS `certificateHost`. Both can support the security outcome. They are server configuration or service bindings, not writable application fetch properties. The inspected [Sites build adapter](../build/sites-vite-plugin.ts) copies hosting metadata and migrations; it does not define either primitive. A local preview binding proves local configuration, not the hosted route.

[Sites Network access](https://learn.chatgpt.com/docs/enterprise/sites#configure-network-access) supports hostname allowlists, not IP/CIDR policies; per-Site exceptions add to inheritance. This is another exact-destination layer when available, but does not document resolved-address filtering. The [strictly-public compatibility flag](https://developers.cloudflare.com/workers/configuration/compatibility-flags/#global-fetch-strictly-public) closes same-zone private-origin routing, rather than promising use of an application's preflight address. The [earlier note](callback-security-alternatives-research.md#actual-connection-filtering-and-range-coverage) records the public-filter source and range caveat: a runtime rule named public need not match the application's entire special-purpose-address deny list.

An HTTP 403 from a fixed private-target probe demonstrates rejection for that request. Without a documented producer or egress observation, it does not show whether rejection happened before DNS, before socket creation, after TLS, at an intermediate proxy, or at the target. A finite set of denied literals also does not prove behavior when a permitted hostname's DNS changes to a forbidden address, mixed answer selection, retry, or connection reuse.

No alternate supported application API was found that avoids these constraints. HTTP CONNECT is not supported by [Workers fetch](https://developers.cloudflare.com/workers/runtime-apis/request/#constructor); WebSocket fetch still relies on its managed HTTP routing. A WebSocket wrapper around raw TCP changes framing, not the TCP destination policy. A Worker native-fetch forwarder simply relocates the same unresolved policy and would change the opaque timer's plaintext boundary. mTLS/signatures/hostname TLS authenticate parties or payloads; they do not prevent the initial non-public socket attempt.

## Falsifiable existing-infrastructure test plan

1. **Native platform filtering:** use the same hosted transport for a positive exact-host HTTPS control and fixed empty HEAD negatives across the relevant IPv4/IPv6 local, private, link-local, reserved and documentation ranges. Disable redirects and bound time/body. Record deployed source/version and sanitized error/status. Distinguish platform denial from timeout, TLS failure and application preflight rejection. Request-level negative fixtures can corroborate filtering; actual rebinding assurance still needs a documented hosted policy or an approved controlled DNS fixture with dial observation.
2. **Literal plus Host:** compare hostname control; freshly validated public literal plus original Host; same literal without Host; fixed invalid-certificate/wrong-host literal with its expected Host; and forbidden/documentation literal plus the same trusted Host. If a forbidden/non-target literal produces the trusted target's normal response, Host routing has falsified address pinning. If literals fail while hostname succeeds, this is not a usable transport. If the positive succeeds and all negatives reject, require an authoritative routing contract or independent destination observation before claiming pinning; rejection could still be input gating or certificate failure.
3. **Node TLS, only where already supported:** count a single custom lookup invocation returning a freshly validated callback literal, retain the original explicit servername, and send no HTTP bytes until secure connection succeeds. Require wrong-host and invalid-certificate negatives to fail. Unsupported option, raw destination denial, or failure of identity negatives eliminates this path. Do not use `authorized` or `remoteAddress` alone as security proof. Do not expand Site or Worker network access to make it pass.
4. **Existing Worker bridge:** first test whether a fixed callback literal is accepted by that Worker's raw socket backend, without calendar data or TLS relaxation. If blocked, further WebSocket or WASM wrapping cannot solve it. A public-address control elsewhere only tests that raw sockets exist; it does not validate the real callback path.
5. **Hosted contract:** inspect the actual produced artifact and supported deployment metadata for an enforceable public-only network binding or fixed target/certificate-host binding. Accept platform-managed dial validation if its hosted scope, retries/fallbacks, TLS identity and denied range coverage meet the requirement. Preserve the known working exact-host transport while recording any unproved portion explicitly.

The public-filter mechanism and operator bindings are credible capabilities, while literal+Host and Node TLS are bounded experiments with clear failure conditions. No researched alternative yet establishes the required hosted guarantee without either additional platform evidence or a successful, independently verified dial-control probe. That is an evidence limit, not proof that paid infrastructure is necessary.
